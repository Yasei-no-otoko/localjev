# Windows ROCm / Radeon 8060S (gfx1151)

This backend runs the original
[`google/diffusiongemma-26B-A4B-it`](https://huggingface.co/google/diffusiongemma-26B-A4B-it)
checkpoint with ROCm PyTorch and Transformers. LocalJev still generates and
validates probability JSON; it does not read option probabilities directly
from logits. The OpenAI-compatible backend implements the text-only subset
needed by LocalJev.

## Requirements

- Windows with a working AMD driver and **ROCm-enabled PyTorch** for gfx1151.
  A CUDA or CPU PyTorch wheel will not work. The backend refuses CPU fallback.
- A Python environment that already passes a ROCm GPU check (Python 3.13 on
  the tested host). See [AMD's Windows PyTorch documentation](https://rocm.docs.amd.com/projects/radeon-ryzen/en/latest/docs/install/installrad/windows/install-pytorch.html)
  for driver and wheel installation.
- Bun **1.4.2 or newer**, matching the upstream lockfile format.
- About **52 GB of disk space for the model**, plus dependencies, and enough
  GPU-accessible memory for FP16 weights and working allocations. A 128 GB
  Strix Halo host is the target; this is not a 4-bit low-memory implementation.

## Set up without changing an existing ROCm environment

Run from the repository root in PowerShell. Set `$RocmPython` to the Python
executable containing your working ROCm PyTorch installation. Do not rely on
an unrelated `python` executable earlier on PATH.

```powershell
$RocmPython = "$env:LOCALAPPDATA\Programs\Python\Python313\python.exe"
& $RocmPython -c 'import torch; assert torch.version.hip and torch.cuda.is_available(); print(torch.__version__); print(torch.cuda.get_device_properties(0))'
& $RocmPython -m venv --system-site-packages .venv-rocm
& .\.venv-rocm\Scripts\python.exe -m pip install -r requirements-rocm.txt
bun install --frozen-lockfile
```

The overlay environment reuses the installed ROCm PyTorch while keeping the
new Transformers version separate. `requirements-rocm.txt` deliberately does
not install PyTorch. No native compilation is required.

## Start both servers

```powershell
.\scripts\start-rocm.ps1
```

The first start downloads the official checkpoint through Hugging Face and
loads it onto the GPU. The launcher waits for the backend before starting
LocalJev. It listens on loopback, uses one in-flight inference request, and
stops its own backend when LocalJev exits. Existing services are never stopped
to free ports. Use another terminal for requests.

For an explicitly downloaded checkpoint, a local model directory also works:

```powershell
.\scripts\start-rocm.ps1 -Model '.runtime/models/diffusiongemma-26B-A4B-it' -LocalFilesOnly
```

The served model identifier is the value passed as `-Model`; the launcher
configures LocalJev to match it. Use `-Python` and `-Bun` for explicit
executables. The launcher also detects the repository-local Bun executable
at `.runtime/bun/bun-windows-x64/bun.exe` when present.

The launcher configures its environment directly and does not load `.env`.
Set optional client authentication in the launching shell:

```powershell
$env:LOCALJEV_API_KEY = 'your-local-client-key'
.\scripts\start-rocm.ps1
```

## Verify the complete HTTP path

```powershell
Invoke-RestMethod http://127.0.0.1:8080/ready
bun run smoke:http
```

`smoke:http` checks readiness, sends a real decision request containing
`choice`, `score`, and `noul`, and validates the returned probabilities and
token usage. It prints the upstream model and elapsed time. If client
authentication is enabled, set `LOCALJEV_API_KEY` in this terminal too.
For a different API URL, set `LOCALJEV_URL`.

For development checks without loading model weights:

```powershell
bun test
bun run typecheck
& .\.venv-rocm\Scripts\python.exe -m unittest discover -s test -p 'test_rocm_server.py'
```

## Backend behavior

- FP16, explicit HIP device placement, SDPA attention and eager PyTorch MoE
  operations are used by default.
  The startup report includes the actual GPU architecture and package versions.
- DiffusionGemma uses its own denoising schedule. Ordinary autoregressive
  `temperature` is not mapped onto that schedule. A dynamic cache avoids the
  Transformers compilation path on Windows.
- JSON schemas are included in the prompt. There is no grammar-constrained
  diffusion decoder; LocalJev retains its validation and corrective retries.
- Generation is serialized and queue admission is bounded. This is a local
  development server, not a public multi-user inference service.
- A different model must be selected explicitly. Generic causal models may
  be used for diagnostics, but their output does not validate DiffusionGemma.

The original oMLX configuration and evaluation results remain available in the
[main README](../README.md). Those measurements were made on a Mac and do not
describe the ROCm backend.

## Verified on September 20, 2026

The official model at revision
`f7f5b7f5fa82ffc52addd066915886d497f5517b` completed a real
`/ready` → `/v1/systemone` request on Windows with the following configuration:

| Component | Validated value |
|---|---|
| GPU | AMD Radeon 8060S, `gfx1151` |
| Python | 3.13.9 |
| PyTorch | `2.15.0a0+rocm10.1.0a20260909` |
| HIP reported by PyTorch | `7.16.26362` |
| Transformers | `5.11.0` |
| Bun | `1.4.2` |
| Model placement | Entire model on `cuda:0` (PyTorch's HIP device API) |
| Inference | FP16, SDPA, eager MoE, dynamic cache |
| Request output ceiling | 512 tokens |
| Input / output tokens | 522 / 72 |
| Full HTTP decision latency | 30.80 seconds; 41.47 seconds after a fresh restart |

The smoke request returned `technical` with probability `0.9`, a frustration
score of `0.9`, and an urgent probability of `0.8`. All three response types
passed validation without a corrective retry in both runs. Each was the first
request after loading. This is an integration check,
not a calibration study or a representative throughput benchmark.

The weights occupy 51,647,701,024 bytes. Loading can temporarily use much more
system memory than the final GPU allocation. These results validate the
listed nightly stack; other ROCm versions require their own runtime check.

Development validation passed 27 Bun tests, 12 Python tests, and the TypeScript
type check. Launcher checks covered Windows PowerShell 5.1 and PowerShell 7,
including failure, timeout, cancellation and child-process cleanup.

## Repeat the bake-off with DiffusionGemma only

[`eval/gfx1151-diffusiongemma-rocmfpx-q8.json`](../eval/gfx1151-diffusiongemma-rocmfpx-q8.json)
retains the September 18 bake-off settings and selects only
`diffusiongemma-26B-A4B-it-Q8_0_ROCMFPX_AGENT.gguf`. It evaluates 40 examples from each of
AG News, BoolQ and SST-5, with 0 and 2,048 background words: 240 measured
requests plus two excluded warm-ups. Seed, sample selection, output budget,
retry policy, 90-second per-attempt timeout and cache-busting policy match
the original run.

The Q8 weights are from
[`kingjones777/DiffusionGemma-26B-A4B-it-ROCmFP4-GGUF`](https://huggingface.co/kingjones777/DiffusionGemma-26B-A4B-it-ROCmFP4-GGUF),
revision `2eeff1460e24a0cf45fb98f0def57099c57823fc`:

- File: `diffusiongemma-26B-A4B-it-Q8_0_ROCMFPX_AGENT.gguf`
- Size: 26,504,415,840 bytes
- SHA-256: `e724f2fb8ecae63d916d7075c776c85d239ca72d7e3c1f9506f0bcf7c2691063`

Save the file under `.runtime/models/diffusiongemma-rocmfpx-q8/`.
This GGUF needs the ROCmFPX fork; the Transformers backend above cannot load it.

Build the pinned ROCmFPX server with an existing native Windows ROCm SDK,
Visual Studio C++ tools, CMake and Ninja:

```powershell
git clone https://github.com/charlie12345/ROCmFPX.git .runtime/ROCmFPX
git -C .runtime/ROCmFPX checkout --detach c49ebdbd5c9f01ec242369f9e7f7967855f80cba
pwsh -File scripts/build-rocmfpx.ps1
```

The build helper defaults to the existing Python 3.13 TheRock SDK, accepts
`-RocmPath` for another installation, and builds with 32 jobs. It applies
[`rocmfpx-http.patch`](../scripts/rocmfpx-http.patch) followed by
[`rocmfpx-json-output.patch`](../scripts/rocmfpx-json-output.patch), including
upgrades from the earlier HTTP-only patch. The build runs 20 model-free
regression cases for output boundaries and schema serialization.
The patches pass each request's seed to the diffusion decoder, add the
requested JSON schema using the FP16 adapter's readable separator style, and
separate model reasoning channels with the existing chat parser. Generated
text is retained until an end-of-generation token or the requested output
limit; repeated numeric tokens are not grounds for truncation.
JSON generation remains **prompt-only**;
LocalJev validates the actual output and applies the original retry policy.
The model's entropy-bound denoising schedule is unchanged.

The pinned fork's `llama-server` includes a DiffusionGemma HTTP path.
`llama-diffusion-gemma-server` is a different, file-based logits service.
Start the HTTP backend in one terminal:

```powershell
$rocmSdk = "$env:LOCALAPPDATA\Programs\Python\Python313\Lib\site-packages\_rocm_sdk_devel"
$env:PATH = "$rocmSdk\bin;$env:PATH"
& .runtime/rocmfpx-build/bin/llama-server.exe `
  -m .runtime/models/diffusiongemma-rocmfpx-q8/diffusiongemma-26B-A4B-it-Q8_0_ROCMFPX_AGENT.gguf `
  --alias diffusiongemma-26B-A4B-it-Q8_0_ROCMFPX_AGENT `
  --host 127.0.0.1 --port 8001 -dev ROCm0 -ngl 999 -fa on `
  -np 1 -c 8192 -b 8192 -ub 8192 -n 256 --seed 20260918 --jinja `
  -t 16 -tb 16 --no-warmup --cache-ram 0 -fit off -lv 4
```

Diffusion requires both context and microbatch capacity for the entire prompt
plus the 256-token canvas. Requests are serialized, and the native server
clears its prompt cache between them.

Then run the evaluation in another terminal, from the repository root:

```powershell
$env:LOCALJEV_UPSTREAM = 'http://127.0.0.1:8001'
bun --no-env-file run scripts/eval/run.ts --config eval/gfx1151-diffusiongemma-rocmfpx-q8.json --out eval/runs/my-gfx1151-q8-bakeoff
```

After the evaluator finishes, record Windows hardware and the backend version,
then regenerate the report. The unchanged evaluator originally collected macOS
metadata. This helper preserves that data in `originalEnvironment`, reads the
current CPU, Windows version and visible RAM through CIM, and refuses a locked
run. Supply the backend name and version that you actually built; the version
below identifies the pinned commit plus this repository's HTTP and output patches.

```powershell
pwsh -File scripts/eval/annotate-windows.ps1 -RunPath eval/runs/my-gfx1151-q8-bakeoff -BackendName ROCmFPX -BackendVersion 'c49ebdb + HTTP and JSON output patches'
bun --no-env-file run scripts/eval/report.ts eval/runs/my-gfx1151-q8-bakeoff
```

No LocalJev HTTP bridge is required: the benchmark calls the production
`Engine` directly. Use a new output directory for each run. To resume an
interrupted run, replace `--out` with `--resume` and keep the same config.

This is the same-input benchmark on **Windows / ROCm / ROCmFPX Q8**. The original
DiffusionGemma result used **macOS / oMLX / MLX 4-bit**. Runtime, precision and
backend prompt handling differ, so their timings do not isolate GPU hardware
performance. See [the evaluation methodology](evaluation.md) for metric
definitions and limitations.

The earlier FP16 run was stopped at the user's request because of PC load.
Its [41/240 partial results](../eval/reports/2026-09-20-gfx1151-diffusiongemma/report.md)
and [configuration](../eval/gfx1151-diffusiongemma.json) are preserved separately;
they are not part of the Q8 evaluation.

The completed [AGENT Q8 report](../eval/reports/2026-09-20-gfx1151-diffusiongemma-q8-rocmfpx/report.md)
contains all 240 measurements, and the
[comparison](../eval/reports/2026-09-20-gfx1151-diffusiongemma-q8-rocmfpx/comparison.md)
places them beside the original DiffusionGemma bake-off result.

### Retest failed Q8 cases with FP16

With the local FP16 backend running on port 8000, replay only the failed rows
from a completed Q8 run:

```powershell
$env:LOCALJEV_UPSTREAM = 'http://127.0.0.1:8000'
bun --no-env-file run scripts/eval/retest.ts --source eval/reports/2026-09-20-gfx1151-diffusiongemma-q8-rocmfpx-standard --model .runtime/models/diffusiongemma-26B-A4B-it --out eval/runs/my-fp16-failure-retest
```

Add `--check-only true` to verify the inputs without model requests or result
files. The replay checks source coverage, data and evaluator hashes, then
matches each original first request byte-for-byte after replacing only the
model identifier. It preserves the source nonce, seeds, 256-token output
limit, 90-second timeout and two corrective retries. Two warm-ups are excluded.
An existing output directory is refused.

The [three-case FP16 retest](../eval/reports/2026-09-20-gfx1151-fp16-sst5-retest/report.md)
records JSON syntax, Engine output validation and classification correctness
separately, including each raw assistant response. This selected subset is
kept separate from both full Q8 reports and the interrupted FP16 evaluation;
it is not an overall accuracy estimate.

### ROCmFPX JSON output correction

The original Q8 reports above predate the JSON output correction. The native
server's repetition heuristic mistook valid compact arrays containing `0.0`
for a loop and cut two SST-5 responses at `{"answers":{"q1":[`. It now stops
only at a model end token or the configured output limit. A separate case
copied `"type":"object"` from the compact schema into the answer; matching
the FP16 adapter's schema separator style resolved that case with the same
model, seed and remaining prompt text.

The [diagnosis and controlled replays](../eval/reports/2026-09-20-gfx1151-diffusiongemma-q8-rocmfpx-json-fixed/diagnosis.md)
record the causes and raw outputs. No generated probabilities are fabricated
or repaired, and output validity remains distinct from classification accuracy.

The [patched standard-Q8 evaluation](../eval/reports/2026-09-20-gfx1151-diffusiongemma-q8-rocmfpx-json-fixed/report.md)
completed all 240 requests: 237 passed on the first attempt. The original three
failures passed their controlled replays, while three different short inputs
still produced malformed JSON directly from the model. This prompt-only backend
does not guarantee valid JSON; the diagnosis retains those failures and their
raw generated tokens.
